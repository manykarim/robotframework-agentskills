# ADR-003: Skill Invocation Strategy — Subprocess `claude -p` with Profile Isolation

**Status:** Accepted
**Date:** 2026-04-14
**Deciders:** System Architecture
**Related:** ADR-002, ADR-005

---

## Context

The evaluation harness needs to run Claude Code repeatedly under controlled conditions:

- Two arms per task: `control` (skills disabled) vs `treatment` (skills enabled).
- N=8 replicates per `(task, arm)` cell to get usable statistics.
- Fresh fixture per run (no state leakage between replicates).
- Captured artifacts: session JSONL, hook logs, stdout stream-json, fixture end-state.
- No cross-contamination: each session must use a distinct session id and a clean CWD.
- Must run headless in CI (no TTY; no human interrupt).

Three invocation strategies are possible:

1. **Subprocess** — spawn `claude -p "…" --output-format stream-json` per cell.
2. **In-process SDK** — embed Anthropic SDK, call Claude directly; reimplement a minimal
   agent loop in Python.
3. **MCP** — drive Claude via the MCP server (treating MCP tools as the eval surface).

The existing project relies heavily on the Claude Code session JSONL format and hook logs
as its measurement substrate (see `claude-code-extension-quality-evaluation.md` §1). The
metrics under measurement (Read:Edit ratio, reasoning loops, user interrupts, etc.) are
artifacts of **Claude Code's own session lifecycle**, not generic LLM interactions.

---

## Decision

**Use subprocess invocation of the `claude` CLI in print mode (`claude -p`), with
`CLAUDE_CONFIG_DIR`-based profile isolation** for the control/treatment arms.

Specifically:

- One OS subprocess per session (one cell = one subprocess).
- `CLAUDE_CONFIG_DIR=<profile_dir>` selects the skill set in effect for that run.
- `--output-format stream-json` gives us structured per-turn output for immediate capture.
- `--max-turns 40` and a wall-clock timeout bound cost per cell.
- `--allowedTools` pins the tool surface (Read, Edit, Write, Bash, `mcp__rf-mcp__*`) so
  both arms see the same capability set except for skills.
- The CWD for each subprocess is a **fresh copy** of the task's fixture, materialized via
  `git worktree add` or `cp -r` by `infrastructure/runner/fixture_copy.py`.
- After the subprocess exits (normal / timeout / non-zero), the runner:
  1. Locates the session JSONL in `~/.claude/projects/<slug>/` by session id.
  2. Filters hook log lines by the session's timestamp window.
  3. Copies JSONL, hook log excerpts, stdout, and the fixture end-state into
     `runs/<batch_id>/<cell_id>/`.
- Concurrency is supported but bounded (4–8 concurrent subprocesses) to avoid model
  rate limits and avoid the "quality collapse at high concurrency" effect described in
  the parent doc §2.3.

### Profile structure

```
profiles/
├── control/
│   ├── CLAUDE.md            ← minimal shared system context
│   ├── skills/              ← no robotframework-agentskills
│   └── .mcp.json            ← same MCP config (rf-mcp is infrastructure, shared)
└── treatment/
    ├── CLAUDE.md            ← identical to control
    ├── skills/
    │   └── robotframework-agentskills/    ← synced from root skills/
    └── .mcp.json            ← identical to control
```

Per-skill treatment profiles (`treatment-skill-A/`, `treatment-skill-B/`, …) are
generated by `profile_manager.py` for leave-one-out attribution studies.

---

## Consequences

### Positive

- **Highest fidelity.** Every metric in the catalog — Read:Edit, user interrupts,
  reasoning loops, hook fire rate — exists *because* of Claude Code's session
  lifecycle. Driving Claude Code itself is the only way to measure them.
- **Zero re-implementation risk.** We do not reimplement the agent loop, tool
  dispatch, hook execution, or skill-loading logic. If Anthropic ships a Claude Code
  change, the harness automatically picks it up.
- **Profile isolation is trivial.** `CLAUDE_CONFIG_DIR` is the official mechanism;
  both arms use it identically — only the skills directory differs.
- **Matches production use.** The eval measures the same code path that end-users
  exercise. There is no "but it works in the SDK" caveat.
- **Hook logs are captured automatically.** Claude Code runs the same hooks in both
  arms; we just read the log files the hooks already write.
- **Parallelizable.** Each subprocess is independent — a batch of 480 cells can run
  8-wide overnight.

### Negative

- **Subprocess overhead per cell** (~1–2 s for CLI startup + model warmup). On a
  batch of 480 cells this is ~10–15 minutes of pure startup time. Mitigated by:
  parallelism; startup is amortized over ~10-minute sessions.
- **Brittle artifact capture.** Session JSONL filename conventions and hook log
  paths can change between Claude Code versions. Mitigated by: record the CC
  version per `RunBatch`; `infrastructure/runner/capture.py` is the single place
  that knows the conventions; unit tests over synthetic JSONL guard against parser
  drift.
- **Rate limits and quotas.** A 480-cell batch consumes significant API credit.
  Mitigated by: cost is budgeted explicitly; replicate counts tunable; weekly
  canary batches kept small (one skill + 10 tasks + 4 replicates).
- **CI runner disk usage.** Session JSONLs can be 50–500 KB each; hook logs larger.
  480 cells ≈ up to 500 MB. Mitigated by: artifact retention policy (30 days for
  PR runs, 1 year for weekly canary); gzip on upload.

### Neutral

- Requires `claude` CLI in the runner PATH. The CI image installs it as a standard
  step (see ADR-005).
- **Invocation in CI vs locally.** The subprocess strategy is identical in both
  environments. Locally we call `claude -p …` directly from
  `infrastructure/runner/claude_cli.py`. In GitHub Actions we drive the same
  subprocess via `anthropics/claude-code-action@v1`, which is a thin wrapper
  that handles auth setup and then invokes `claude -p` with the same flags.
  From this ADR's perspective — the *invocation layer* — nothing changes:
  one OS subprocess per cell, `--output-format stream-json`, `--max-turns`,
  `CLAUDE_CONFIG_DIR` profile isolation, session JSONL capture. The choice
  between `CLAUDE_CODE_OAUTH_TOKEN` (subscription billing) and
  `ANTHROPIC_API_KEY` (per-token billing) is interchangeable at the
  invocation layer — they simply set different env vars that the same
  `claude` binary consumes. See ADR-005 "Authentication" for how that choice
  is made and its rate-limit / cost / security implications.

## Alternatives Considered

### In-process SDK (embed `anthropic` directly)

- **Pros:** Fastest per-turn (no subprocess overhead); easy to mock in tests.
- **Cons:** Would require reimplementing Claude Code's agent loop, tool dispatcher,
  skill loader, and hook runtime. None of the session-lifecycle metrics (Read:Edit,
  reasoning loops on *internal* thinking, user interrupt semantics) would be
  measurable because those phenomena are specific to Claude Code's session model.
  Also: SDK and CLI behavior drift; measuring the SDK does not measure the
  production product.
- **Why rejected:** Fatal fidelity loss. We would be measuring the wrong artifact.

### MCP as the eval surface (drive the MCP server's tools, not Claude Code itself)

- **Pros:** Measures the tool-execution path deterministically; no LLM variance.
- **Cons:** Skills are **context**, not tools. Their job is to change how the agent
  *thinks*, not what tools it has. Evaluating the MCP server by calling its tools
  directly tells us nothing about whether a `SKILL.md` improves agent behavior.
  MCP-only evaluation would answer a completely different question (is the MCP
  server correct?) and is already served by the plugin's pytest suite.
- **Why rejected:** Wrong unit of analysis.

### Hybrid (SDK for unit-level metrics, CLI for end-to-end)

- **Pros:** Could speed up narrow-task runs.
- **Cons:** Two invocation paths to maintain; metric definitions would diverge
  ("SDK Read:Edit" vs "CLI Read:Edit" are not comparable); cross-cutting bugs
  ("works in SDK, broken in CLI"); narrow tasks are already only ~5 minutes each,
  so the speedup is marginal.
- **Why rejected:** Not worth the maintenance burden for a small speedup.

### Container per session (Docker container as the isolation boundary)

- **Pros:** Stronger fixture isolation; easier to reproduce "clean machine"
  environments.
- **Cons:** Container startup (~3–10 s) dominates session time for narrow tasks;
  image build/maintenance overhead; Docker-in-Docker complications in GH Actions;
  the `cp -r` fixture approach is already sufficient for file isolation.
- **Why rejected:** Overkill. Revisit if we see cross-session contamination in
  practice (unlikely given fresh fixtures + distinct session IDs).

## Implementation Notes

- `infrastructure/runner/claude_cli.py` is the **only** place that shells out to
  `claude`. The rest of the domain sees a `SessionExecution` aggregate.
- Capture uses the session id returned by `--output-format stream-json` to locate
  the JSONL deterministically. Do **not** rely on "newest file in directory"
  heuristics — concurrent runs break them.
- Hook log parsing must filter by `session_id` when available, and only fall back
  to timestamp windows when the hook doesn't record session id.
- Timeouts are enforced via `subprocess.run(..., timeout=…)` + `SIGTERM` escalation
  to `SIGKILL` after 10 s grace. A timed-out cell is a valid data point
  (`InvocationOutcome.timeout`), not a failure to re-run.
